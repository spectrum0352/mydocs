# Trojan Horses: Development and Deployment (Security Research Perspective)

**Trojan horses** are malicious programs that **disguise themselves as legitimate software** to trick users into running them. Modern attackers rarely write Trojans entirely from scratch. Instead, they use specialized tools and services (often called *malware kits* or *services*) to assemble custom Trojans with minimal effort. These kits provide modular payloads (keyloggers, RATs, data stealers, etc.), configuration options, and built‑in obfuscation. For example, security researchers observed that a Russian “Trojan construction kit” allowed hackers to **“recompile and pack the malicious code in countless subtly different ways so as to evade detection”**[\[1\]](https://www.computerworld.com/article/1572840/hackers-use-construction-kit-to-unleash-trojan-variants.html#:~:text=What%20makes%20the%20threat%20from,and%20block%20threats%2C%20Jackson%20said). In practice, a kit might let an attacker choose payload components, configure network callbacks, and then output a ready‑to‑run Trojan executable.

- **Trojan Construction Kits:** These are pre‑built frameworks (often GUI tools or scripts) that let even non‑expert attackers build customized Trojans. Kits like **Dark Horse Trojan Virus Maker**, **Senna Spy Trojan Generator**, **Trojan Horse Construction Kit v2.0**, and **Progenic Mail Trojan Construction Kit** have circulated in underground forums. They typically allow script kiddies to configure attacks (e.g. overwrite the MBR, steal data, log keystrokes) and automatically wrap those functions into a standalone Trojan[\[2\]](https://www.vskills.in/certification/tutorial/trojans/#:~:text=,and%20list%20and%20control%20processes)[\[1\]](https://www.computerworld.com/article/1572840/hackers-use-construction-kit-to-unleash-trojan-variants.html#:~:text=What%20makes%20the%20threat%20from,and%20block%20threats%2C%20Jackson%20said).
- **Malicious Modules (Payloads):** Kits include modules such as backdoors/RATs, keyloggers, credential stealers, spam-senders, or encryption routines. The attacker selects modules like “data exfiltration,” “remote shell,” or “encrypt files for ransom,” and the kit builds an executable with those capabilities.
- **Obfuscation and Crypters:** To avoid antivirus detection, Trojans are often processed through **crypters** or **packers**. A crypter is a service or tool that encrypts or transforms the malicious binary. For instance, a recent commercial crypter called **“Ghost Crypt”** was advertised on hacker forums; it supported packing both EXE and DLL payloads with advanced evasive features (full AV bypass, browser download bypass, and a 99% polymorphic engine)[\[3\]](https://www.esentire.com/blog/ghost-crypt-powers-purerat-with-hypnosis#:~:text=As%20seen%20in%20Figure%202%2C,both%20EXE%20and%20DLL%20files)[\[4\]](https://www.esentire.com/blog/ghost-crypt-powers-purerat-with-hypnosis#:~:text=,and%20AVs%20can%20be%20bypassed). Such crypters provide user-friendly GUIs and hide the Trojan’s signature, making detection much harder[\[5\]](https://www.esentire.com/blog/pure-crypter-malware-analysis-99-problems-but-detection-aint-one#:~:text=This%20quota%20system%20appears%20to,operations%20without%20extensive%20technical%20expertise).

### Trojan Build Process (Conceptual Workflow)

1.  **Select or Write Payload Code:** The attacker chooses or codes the core malware functions (e.g. a reverse shell, password stealer, remote admin tool). This code may be open-source (e.g. an existing RAT) or custom.
2.  **Configure the Trojan:** Using a construction kit or manual configuration, the attacker sets options: what files to target, what data to exfiltrate, network C2 (command & control) addresses, etc. Kits often offer toggles for features (startup persistence, encryption, error suppression).
3.  **Package with a Wrapper/Dropper:** The malicious payload is then “wrapped” or bound to a benign carrier file so the user won’t suspect it. Tools can bind a trojan DLL to a legitimate EXE, or append a malicious script to a PDF or Office document. A common strategy is a **dropper**: a small innocent‑looking executable (e.g. “update.exe” or a fake invoice PDF) that, when run, drops and launches the main Trojan. Wrappers ensure the Trojan runs invisibly while showing the legitimate program’s interface.
4.  **Apply Crypter/Obfuscator:** The combined Trojan payload is processed through a crypter/packer. For example, an attacker might submit their Trojan DLL to a service like Ghost Crypt, which encrypts it and attaches an unpacking stub. The crypter’s GUI (e.g. PureCrypter) provides many evasive options – AMSI/EDR bypasses, debug checks, delay timers, anti‑VM checks, etc. – to make the malware hard to analyze[\[6\]](https://www.esentire.com/blog/pure-crypter-malware-analysis-99-problems-but-detection-aint-one#:~:text=As%20illustrated%20in%20the%20figure,of%20the%20available%20features%20include).
5.  **Test and Iterate:** The attacker can test the packed Trojan against antivirus engines (some crypter services include scan test tools) and tweak options until detection is minimal.

By the end of this process, the attacker has a final **Trojan executable** that appears harmless or legitimate. For example, eSentire researchers described a 2025 case where attackers created a trojanized copy of a PDF viewer (“hpreader.exe”) that sideloaded a malicious DLL via a crypter. The result was a trojanized reader that appeared to open tax documents normally while secretly injecting PureRAT code into the system[\[3\]](https://www.esentire.com/blog/ghost-crypt-powers-purerat-with-hypnosis#:~:text=As%20seen%20in%20Figure%202%2C,both%20EXE%20and%20DLL%20files)[\[4\]](https://www.esentire.com/blog/ghost-crypt-powers-purerat-with-hypnosis#:~:text=,and%20AVs%20can%20be%20bypassed).

### Example – Modular Trojan Construction (Attack Scenario)

1.  **Payload Creation:** An attacker decides to use PureRAT (a known Remote Access Trojan) and write a custom malicious DLL that loads it.
2.  **Wrapper (Sideloading):** They take a legitimate EXE (e.g. a PDF reader) and configure a loader (e.g. using PowerShell or a dropper tool) to load the malicious DLL when the EXE is launched.
3.  **Crypter (Obfuscation):** They upload the malicious DLL and dropper EXE to a crypter service like Ghost Crypt[\[3\]](https://www.esentire.com/blog/ghost-crypt-powers-purerat-with-hypnosis#:~:text=As%20seen%20in%20Figure%202%2C,both%20EXE%20and%20DLL%20files), enabling DLL sideloading and AV bypass. The crypter outputs a “clean” EXE+DLL set.
4.  **Delivery & Execution:** The final trojan payload is delivered (e.g. emailed as a supposed tax document). When the victim opens the file, the EXE runs (showing the real program) and simultaneously the DLL decrypts and injects PureRAT into a running process. The user is unaware while the attacker gains a hidden remote shell.

## Distribution and Delivery

Once built, Trojans are spread using social engineering and exploitation:

- **Phishing Emails & Malspam:** Attackers often send the Trojan in emails as malicious attachments (office docs with macros, PDFs, or ZIPs). The dropper may be embedded inside or linked from the attachment. Victims are tricked by urgency/familiar context (e.g. “invoice enclosed,” “account update,” or targeted spear-phish messages).
- **Fake Downloads & Websites:** Trojans can be disguised as cracked software, updates, or utilities on malicious or compromised sites. Drive-by-download kits exploit browser/Flash/Java vulnerabilities to fetch the Trojan.
- **Exploits and Exploit Kits:** Unpatched software flaws are exploited to drop Trojans. Commercial “exploit kits” scan victims’ browsers or network for vulnerabilities (e.g. old Flash/Java/IE bugs) and then install the Trojan without user action.
- **Portable Media and Direct Access:** In targeted attacks, a compromised USB stick or local network share can deliver a Trojan. Physical access or compromised developer credentials (e.g. in a CI/CD pipeline) could inject a Trojan into cloud images or install scripts.

In all cases, the Trojan tries to hide its presence. It may disable security tools, use common processes (LOLBins) to execute, or check for analysis environments. For example, PureCrypter-enabled Trojans included checks for debuggers, virtualization, sandbox DLLs, and even screen resolution to avoid running in a researcher’s lab[\[6\]](https://www.esentire.com/blog/pure-crypter-malware-analysis-99-problems-but-detection-aint-one#:~:text=As%20illustrated%20in%20the%20figure,of%20the%20available%20features%20include).

## Trojans in Cloud Environments (Azure and Others)

In cloud settings like **Microsoft Azure**, the classic “Trojan executable” adapts to a cloud context. Attackers may embed malicious code into cloud services or infrastructure as follows:

- **Cloud Resources as Carriers:** Azure Blob storage or file shares can host malware. The Microsoft Security blog notes that **threat actors can place malicious executables or macro documents in public or weakly secured Azure Blob containers**, so victims who download from those URLs unknowingly fetch malware[\[7\]](https://www.microsoft.com/en-us/security/blog/2025/10/20/inside-the-attack-chain-threat-activity-targeting-azure-blob-storage/#:~:text=Threat%20actors%20may%20attempt%20to,directly%20from%20those%20blob%20URLs). In one campaign, attackers staged payloads in blob storage to *download* by compromised users.
- **Compromised Containers and VMs:** An attacker with cloud access might push a backdoored container image to an Azure Container Registry or run a trojan payload on an Azure VM. For example, they could upload a Trojanized web app or API function. In one cloud breach, adversaries rapidly created short-lived Azure VMs (just a few hours long) to run password sprays and host malicious scripts, then destroyed them to avoid detection[\[8\]](https://techcommunity.microsoft.com/blog/microsoftsecurityexperts/cloud-shadows-how-attackers-exploit-azure%E2%80%99s-elasticity-for-stealth-and-scale/4463551#:~:text=Once%20access%20was%20established%20using,term%20detection).
- **Serverless/SaaS Hijacking:** Azure Functions, Logic Apps, or DevOps pipelines can be corrupted. A malicious Azure Function (triggered by a blob upload) could run Trojan-like code (e.g. data exfiltration, command execution). An attacker might also insert backdoors into IaC templates (ARM/Bicep) or exploit pipeline credentials to deploy a trojan. The “Elasticity” case study shows how attackers abused cloud-native features (notably ML workspaces, storage, and OAuth apps) for persistence[\[9\]](https://techcommunity.microsoft.com/blog/microsoftsecurityexperts/cloud-shadows-how-attackers-exploit-azure%E2%80%99s-elasticity-for-stealth-and-scale/4463551#:~:text=Blob%20storage%20exploitation%3A%20payload%20staging,and%20data%20exfiltration). For instance, they used Azure Blob containers to **stage scripts and exfiltrate data**, leveraging Blob’s high availability as a covert channel[\[9\]](https://techcommunity.microsoft.com/blog/microsoftsecurityexperts/cloud-shadows-how-attackers-exploit-azure%E2%80%99s-elasticity-for-stealth-and-scale/4463551#:~:text=Blob%20storage%20exploitation%3A%20payload%20staging,and%20data%20exfiltration).
- **Identity and API Abuse:** Instead of dropping a file, attackers may use stolen Azure credentials to spawn “Trojan-like” processes. Examples include registering malicious OAuth apps as backdoors or enabling high-privilege roles via Azure AD. MITRE ATT&CK for Cloud includes techniques like *Obtain Cloud Instance Metadata* or *Create Cloud Instance* to reflect these flows. In short, an “Azure Trojan” might be malicious code running in a cloud VM or function, or a hidden cloud principal with overprivileged access – both allow remote control or data theft.

**Example (Azure Attack):** A notable Azure-based campaign (2024) involved attackers creating blob storage containers to host Trojan scripts and files[\[9\]](https://techcommunity.microsoft.com/blog/microsoftsecurityexperts/cloud-shadows-how-attackers-exploit-azure%E2%80%99s-elasticity-for-stealth-and-scale/4463551#:~:text=Blob%20storage%20exploitation%3A%20payload%20staging,and%20data%20exfiltration). By uploading malware to these blobs, they tricked downstream Azure Functions into executing malicious tasks. They also used Azure Key Vaults to store stolen credentials, ensuring persistence. This illustrates that in cloud attacks, Trojans manifest as **malicious cloud artifacts** (functions, scripts, containers) rather than just .exe files.

## Mapping to MITRE ATT&CK

From the MITRE ATT&CK perspective, building and deploying a Trojan spans many techniques across tactics:

- **Initial Access:** T1566 (*Phishing*) or T1190 (*Exploit Public-Facing Application*) to deliver the Trojan.
- **Execution:** T1059 (Command/PowerShell scripts as dropper), T1204 (User Execution of a Trojanized file).
- **Persistence:** T1547 (Boot or Logon Autostart), T1176 (Browser Extensions) – e.g., the Trojan may add a registry Run key.
- **Privilege Escalation:** T1548 (Abuse Elevation Control Mechanism) if the Trojan exploits UAC bypass or sideloading.
- **Defense Evasion:** T1027 (Obfuscated Files or Information) – trojans use crypters and packers. T1497.001 (Virtualization/Sandbox Evasion) – crypter stubs check for VMs. T1140 (Deobfuscate/Decode Files) – malware unpacks itself at runtime.
- **Credential Access:** T1056 (Input Capture) – a trojan keylogger. T1552 (Unsecured Credentials) – trojan might steal stored passwords.
- **Lateral Movement:** T1563 (Remote Service Hijacking) – trojans like RATs can pivot inside a network.
- **Command & Control:** T1071 (Standard Application Layer Protocol) – trojans often contact C2 via HTTP/HTTPS.
- **Exfiltration:** T1041 (Exfiltration Over C2 Channel) or T1537 (Transfer Data to Cloud Account) – trojans may exfiltrate data to attacker-controlled servers or cloud storage.

For **Azure-specific** context (outside ATT&CK’s core matrix), attackers often abuse cloud management APIs (e.g. creating malicious Azure Resources). Techniques such as *Azure Create or Modify VM* or *Register Application (Azure OAuth app)* correspond to attacker-controlled trojan functions in the cloud. In defensive terms, AWS/Azure security controls mapping to ATT&CK exist (e.g. detecting upload of executables to storage accounts), but the principle is the same: treat malicious cloud scripts and accounts as you would a Trojan on-prem.

## Defensive Guidance and Safe Testing

Understanding Trojan creation is primarily a defensive exercise. **Ethical guidelines** are paramount: **Do not build or deploy malicious code in uncontrolled environments.** Use secure, isolated labs. For learning or pentesting, consider these best practices:

- **Controlled Sandbox Environments:** Use virtual machines (VMs) or containers that are completely isolated from production networks. Snapshots/rollbacks allow safe testing of payloads. **Never connect a Trojan sample to the internet outside of a lab.** Emulators and malware analysis sandboxes (e.g. Cuckoo, ANY.RUN) can safely run trojans and observe behavior.
- **Dummy Payloads for Simulation:** Instead of real Trojans, use benign programs that simulate trojan behavior (e.g. open a reverse shell to a controlled server, or log keystrokes into a file) during exercises. This avoids legal/ethical issues while practicing detection and response.
- **Deep Packet and Process Monitoring:** To study a Trojan’s methods, monitor all network traffic and system changes during execution. Tools like Procmon, network sniffers, and memory scanners reveal dropper actions, injected DLLs, and API calls. Keep logs of created registry keys, new processes, and file writes. Such instrumentation helps reverse-engineer the attack flow.
- **Use Known Threat Intelligence:** Leverage MITRE ATT&CK, vendor reports, and malware databases to recognize patterns. For example, eSentire and Microsoft publish detailed blogs on real trojan campaigns[\[10\]](https://www.esentire.com/blog/ghost-crypt-powers-purerat-with-hypnosis#:~:text=In%20May%202025%2C%20eSentire%27s%20Threat,surge%20in%20infections%20in%202025)[\[9\]](https://techcommunity.microsoft.com/blog/microsoftsecurityexperts/cloud-shadows-how-attackers-exploit-azure%E2%80%99s-elasticity-for-stealth-and-scale/4463551#:~:text=Blob%20storage%20exploitation%3A%20payload%20staging,and%20data%20exfiltration). Updating AV/EDR tools with the latest detections (YARA rules, IOC feeds) helps catch known trojan strains and techniques.
- **Endpoint Protection:** Ensure robust security on endpoints. Modern EDR solutions can detect packer/unpacker behavior, API hooks, or anomalous processes. For instance, an EDR might flag the CreateProcessW(DEBUG_ONLY_THIS_PROCESS) injection technique used by Ghost Crypt as suspicious.
- **Cloud Security:** In Azure and other clouds, apply the principle of least privilege. Monitor for unusual resource creation (unexpected VMs, new OAuth apps), and audit blob storage accesses. Tools like Microsoft Defender for Cloud can alert on anomalous blob uploads or script executions. Enforce MFA and secure identity (to prevent attackers from easily dropping cloud Trojans).
- **User Training and Phishing Defense:** Educate users to recognize phishing. Since Trojans often rely on social engineering, simulated phishing campaigns and caution with attachments can stop many attacks at the outset.

**Key Takeaway:** Trojan development in adversary hands has become commoditized. *Construction kits* and *crypters-as-a-service* allow quick creation of versatile malware[\[1\]](https://www.computerworld.com/article/1572840/hackers-use-construction-kit-to-unleash-trojan-variants.html#:~:text=What%20makes%20the%20threat%20from,and%20block%20threats%2C%20Jackson%20said)[\[6\]](https://www.esentire.com/blog/pure-crypter-malware-analysis-99-problems-but-detection-aint-one#:~:text=As%20illustrated%20in%20the%20figure,of%20the%20available%20features%20include). By studying these tools and methods – always within legal, sandboxed labs – defenders can anticipate attacker strategies and strengthen detection. For example, knowing that Ghost Crypt advertises *“guaranteed bypasses for Windows Defender”*[\[3\]](https://www.esentire.com/blog/ghost-crypt-powers-purerat-with-hypnosis#:~:text=As%20seen%20in%20Figure%202%2C,both%20EXE%20and%20DLL%20files) underscores the need for behavior-based detection, not just signature scanning. Ultimately, awareness of how Trojans are built and delivered (from phishing lures to packer configs) is crucial to designing effective security controls and training programs.
